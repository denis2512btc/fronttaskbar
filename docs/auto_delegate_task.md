# Постановка: автоматическое назначение при разбиении задачи (выбор участников + роли на бэкенде)

## Цель

При разбиении задачи на карточки пользователь **вручную формирует список участников**, участвующих в этом запросе: по умолчанию выбраны **все участники доски**, снимаемые галочкой исключаются из массива, отправляемого на бэкенд. **Распределение подзадач по ролям и исполнителям выполняет бэкенд**, опираясь на переданный состав и роли участников.

---

## Фронтенд

### UX и поведение

1. В модальном окне «Разбить задачу» добавить блок **«Участники для этого разбиения»**:
   - список строк: участник доски (отображаемое имя / email), **роль на доске** (slug или локализованная подпись — как принято в приложении), чекбокс «участвует»;
   - при открытии окна **все участники доски включены** (все чекбоксы включены);
   - пользователь может **снять галочку** — такой участник не попадает в тело запроса к API разбиения.

2. Данные участников брать из источника правды по доске (например, тот же запрос, что для участников в настройках доски): минимум `user_id`, отображаемое имя, **идентификатор роли компетенции на доске** (`competency_role_id`) и при необходимости **slug роли** для отображения и для бэкенда.

3. Валидация перед отправкой:
   - если после снятия галочек **никто не выбран** — показать ошибку и не вызывать API;
   - текст задачи и колонка назначения — по текущим правилам приложения.

4. Запрос к сервису разбиения расширить: помимо текста задачи передавать **массив выбранных участников**, каждый элемент содержит как минимум:
   - `user_id` (UUID),
   - `competency_role_id` (UUID) **или** договориться о поле `role_slug` — см. контракт ниже.

5. Ответ сервиса разбиения должен позволять создать задачи с **разными исполнителями по карточкам**:
   - если бэкенд возвращает на каждую подзадачу `assignee_id` (или эквивалент), фронт при батч-создании задач подставляет **исполнителя из каждого элемента**;
   - если бэкенд возвращает только `role_id` / `role_slug`, фронт **детерминированно** сопоставляет роль одному из выбранных участников с этой ролью (правило зафиксировать: например, первый в списке, или явно описать на бэкенде что возвращается всегда `user_id`).

6. Ошибки API (неизвестный участник, роль без кандидата в переданном массиве и т.д.) показывать пользователю сообщением из ответа или общим текстом.

### Нефункциональное

- Не ломать сценарий без настроенного URL разбиения и без участников (краевые случаи описать отдельно).
- Сохранить текущий поток: после успешного разбиения — запись промпта (если есть) и создание карточек в выбранной колонке.

## Бэкенд (сервис разбиения)

### Контракт запроса (пример структуры)

Расширить текущий `POST` (тело JSON):

- `prompt` — строка, описание задачи для модели (как сейчас на фронте).
- `members` — массив объектов (только те, у кого на фронте оставили галочку), например:

```json
{
  "prompt": "…",
  "members": [
    { "user_id": "uuid", "competency_role_id": "uuid" },
    { "user_id": "uuid", "competency_role_id": "uuid" }
  ]
}
```

При необходимости добавить опционально `role_slug` для отладки или дублирования — но источник истины для логики должен быть согласован с фронтом (один набор полей).

### Поведение

1. Учитывать **только** переданный массив `members`: назначать исполнителей **только из этих пар** `(user_id, role_id)`; не подставлять пользователей доски, которых не передали.

2. При разбиении текста из `prompt` на элементы `items[]` для **каждой** подзадачи определить исполнителя с учётом ролей:
   - правила приоритета ролей для типов работ — зафиксировать в документации сервиса (или эвристика модели с явными ограничениями);
   - если для подзадачи нет подходящего человека в `members`, вернуть **явную ошибку** (4xx + текст/код) или пометить элемент флагом — заранее выбрать стратегию и описать её.

### Контракт ответа

Расширить элементы массива `items`:

- обязательно сохранить совместимые поля: `title`, `description`, `color` (как сейчас);
- добавить поле назначения, например одно из:
  - **`assignee_id`** (UUID) — предпочтительно для простого фронта; значение **обязано** входить в переданные `user_id` из `members`;
  - или **`competency_role_id`** + правило на фронте (хуже, дублирование логики).

**Рекомендация:** в ответе на каждую карточку возвращать **`assignee_id`**, уже выбранный бэкендом из переданного списка.

### Валидация на бэкенде

- Пустой `members` — ошибка.
- Дубликаты `user_id` в одном запросе — политика: запретить или принять последний (зафиксировать).
- Несуществующие UUID — по возможности отвергать запрос с понятным сообщением.

## Согласование между командами (чеклист)

| Тема | Решение |
|------|--------|
| Идентификация роли в запросе | `competency_role_id` и/или `role_slug` |
| Что возвращает разбиение | минимум `assignee_id` на item |
| Нет кандидата для роли | ошибка целиком vs частичный успех |
| Один пользователь — несколько ролей на доске | как передаётся в `members` (одна строка или несколько) |

---

## Разбиение на задачи в трекере

1. **Бэкенд:** контракт API разбиения + логика назначения по ролям из `members`.
2. **Фронт:** UI выбора участников (чекбоксы, по умолчанию все), расширение клиента `requestTaskBreakdown`, сохранение задач с **per-item** `assignee_id` в батче.
